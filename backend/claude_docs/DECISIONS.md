# Decisions

Lightweight ADRs. Each has a status. **Proposed** means it was decided here, by Claude, to
make this spec buildable — it has not been confirmed with the client and should be treated
as a strong default, not a locked requirement. **Accepted** means the team has actually
signed off on it. Nothing in this file should silently flip from Proposed to Accepted —
that transition should happen because a human said so.

---

## ADR-001: Unlock code = member ID + TOTP, not the raw CTF flag

**Status:** Proposed — needs client confirmation before implementation locks in.

**Context:** The original project notes describe two mechanisms that aren't actually the
same thing: "students get codes through CTF challenges" (suggests the flag itself is the
credential) and "Authenticator or any code providing service... to sync the codes" (suggests
TOTP). Shipping code against both simultaneously produces two different validation code
paths that will drift and contradict each other.

**Decision:** The unlock credential is a personal TOTP code (RFC 6238), generated by a
standard authenticator app, entered together with the student's 4-digit member ID
(`memberid + totp`, 10 digits total, no separator). Solving a challenge grants *eligibility*
to use that already-provisioned TOTP code within a time window — it does not generate a new
code or expose the flag as a credential.

**Why not the raw flag:** flags are frequently shared publicly once a challenge closes or a
writeup is posted. A system where "anyone who ever saw this flag can open the fridge" has no
real access control once the flag leaks, which defeats the purpose of a project literally
built to demonstrate security concepts to a security club.

**Consequences:** Requires an enrollment step (QR code scan into an authenticator app) that
doesn't exist in the original notes — this is new scope, not free. The device firmware and
backend both get simpler than a raw-flag scheme would suggest, because TOTP validation is a
solved, well-tested problem (`pyotp` does the hard part) rather than something built from
scratch.

**If rejected:** the alternative is documented informally as "flag-is-credential" — the
backend issues a short-lived opaque token tied 1:1 to a specific flag submission, which the
student types in directly. This is simpler to build but has the flag-leak problem above and
does not match the "Authenticator" language in the original notes at all. Flag this tradeoff
to the client explicitly rather than silently picking one.

## ADR-002: ESP32 over Arduino Mega or Raspberry Pi Pico

**Status:** Proposed.

**Context:** Original hardware notes list "Arduino Mega" and treat microcontroller choice as
open. The client's requirement (WiFi connection to the CTF range) rules out a plain Arduino
Mega, which has no WiFi radio.

**Decision:** ESP32, using the ESP-IDF framework rather than the Arduino compatibility layer,
for hardware crypto acceleration and proper TLS support via mbedTLS.

**Consequences:** Firmware is C/C++ against ESP-IDF APIs, a steeper learning curve than
Arduino-style `.ino` sketches, but necessary for the TLS and secure-storage properties this
project's own security premise depends on.

## ADR-003: REST polling for v1 realtime updates; WebSocket deferred

**Status:** Proposed.

**Context:** The dashboard needs to reflect unlock events without a manual refresh.
WebSocket, Server-Sent Events, and MQTT were all considered.

**Decision:** v1 ships with the frontend polling `GET /dashboard/unlock-events` and
`GET /devices` every 3-5 seconds. A WebSocket endpoint is specified in `API_SPEC.md` for v2
but should not be built until polling is working end-to-end in a live demo.

**Consequences:** Dashboard updates lag by up to ~5 seconds. Acceptable for this project's
actual use case (an instructor glancing at a dashboard), not acceptable if a future
requirement needs sub-second feedback — revisit then, not preemptively.

**Update following ADR-006:** now that the database is Supabase, its built-in Realtime
feature is a better v2 candidate than the custom `/ws/dashboard` endpoint this ADR
originally pointed to — see `ARCHITECTURE.md` §6. The "don't build v2 until v1 works" part
of this decision still stands regardless of which v2 gets picked.

## ADR-004: CTF range webhook requires HMAC signature verification

**Status:** Proposed — actual mechanism depends on what the range's platform supports.

**Context:** The webhook endpoint (`POST /events/flag-captured`) is reachable by anyone who
knows the URL unless it's protected. An API key alone is phishable/leakable in logs; HMAC
over the payload is the standard pattern for inbound webhooks (same approach Stripe and
GitHub use).

**Decision:** Require an `X-Range-Signature` header containing an HMAC-SHA256 of the raw
request body, keyed with a shared secret (`RANGE_WEBHOOK_SECRET`). Reject unsigned or
incorrectly signed requests with 401 before any processing.

**Open dependency:** this assumes the CTF range platform can be configured to sign its
webhook calls. If it can't, fall back to a long, random, single-purpose bearer token in the
URL path — worse, but functional. Confirm with whoever administers the range before building
this endpoint.

## ADR-005: 4x4 keypad as the v1 input device

**Status:** Proposed.

**Context:** Earlier drafts of the hardware plan never specified how a student physically
enters a code — this was a gap, not a decision.

**Decision:** A wired 4x4 matrix keypad for v1. A Bluetooth companion-app entry flow is a
plausible v2 but depends on ADR-001 being settled first, since the code format an app would
submit differs from what a 10-key keypad can produce.

**Consequences:** Keypad entry of a 10-digit code is mildly clunky but requires no app
development, no pairing flow, and no phone-compatibility testing — the right tradeoff for a
first working version.

## ADR-006: Supabase as the database, used as plain managed Postgres

**Status:** Accepted (per team's explicit direction).

**Context:** The team chose Supabase over self-hosted Postgres or another managed Postgres
provider.

**Decision:** The backend connects to Supabase's Postgres over a standard connection string
via SQLAlchemy, exactly as it would connect to any other Postgres instance. None of
Supabase's own Auth, its client-side auto-generated REST API, or its JS/Python client SDK
are used for the write paths in this system — the FastAPI backend remains the only writer,
per the architecture's original trust boundary. The one scoped exception is Supabase
**Realtime**, which the frontend may subscribe to directly for read-only live updates to the
dashboard (see `ARCHITECTURE.md` §6), gated behind Row Level Security policies.

**Why not use Supabase's client SDK end-to-end (the "default" Supabase app pattern):** that
pattern relies on RLS policies to enforce all business rules, including eligibility
consumption and rate limiting on `validate-code`. Those two specifically need to be atomic,
server-side, and hard to get right even in application code — reimplementing them as RLS
policies and Postgres functions is more error-prone for this team than keeping that logic in
Python, not less. Using Supabase as "just Postgres" for writes is the conservative choice and
the right one here.

**Consequences:** The team gets managed backups, point-in-time recovery, and connection
pooling for free (see `ARCHITECTURE.md` §7), at the cost of not using most of what makes
Supabase distinctive. That's a fine trade for this project — being a full Supabase-native app
was never a goal, having a database someone else operates was.

## ADR-007: Clerk for admin/instructor authentication

**Status:** Accepted (per team's explicit direction).

**Context:** The original spec had the backend issuing its own JWTs against bcrypt-hashed
passwords (`POST /auth/login`). The team chose to use Clerk instead.

**Decision:** Clerk owns instructor/admin sign-up, sign-in, session management, and
credential storage entirely. The frontend integrates Clerk's SDK directly. The backend's only
responsibility is verifying the Clerk-issued session JWT on every admin-protected request
against Clerk's published JWKS — it never sees a password and never issues a token itself.
`POST /auth/login` is removed from the API surface; see `API_SPEC.md` § Auth for the
verification approach and a reference implementation sketch.

**Scope boundary — read this before extending auth to anything else:** Clerk covers
instructors/admins only. It does not cover:
- **Devices.** The ESP32's `X-Device-Key` header is unrelated to Clerk and stays exactly as
  originally specified — a device is not a Clerk user and should never be modeled as one.
- **Students.** Students don't log into anything in this system; they type a code on a
  physical keypad. Their identity is `member_id` plus a backend-managed TOTP secret (ADR-001),
  entirely separate from Clerk. If a future version adds a student-facing portal or app,
  *that* would be a reasonable place to add students as Clerk users — but that's new scope,
  not implied by this decision.
- **The CTF range webhook.** Authenticated by HMAC signature (ADR-004), not Clerk — a webhook
  caller isn't a human with a Clerk session.

**Consequences:** No password storage, no password-reset flow, no bcrypt dependency, less
code for this team to secure and maintain. The tradeoff is an external dependency on Clerk's
availability for every admin dashboard login — acceptable for this project's scale and stakes.
