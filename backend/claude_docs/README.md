# FRZR BURN

A CTF-gated smart mini fridge for the Islander Cyber Society (ICS). Students unlock the
fridge with a code they become eligible for by solving challenges on ICS's CTF range, and
spend CTF-earned credits on items stocked inside.

## Status

MVP in active design. Core architecture decisions are recorded in [`docs/DECISIONS.md`](docs/DECISIONS.md)
— read that file before writing code that touches the code-validation flow, the data model,
or the realtime update mechanism. Several decisions there are marked **Proposed** pending
client sign-off; do not treat them as immutable, but do not silently deviate from them either
— flag the conflict instead of guessing.

## Tech stack

| Layer | Choice | Notes |
|---|---|---|
| Backend | Python 3.12, FastAPI, Pydantic v2 | Async throughout |
| Database | Supabase (managed Postgres) | Backend connects via a direct Postgres connection string, not Supabase's client SDK — see ADR-006 |
| Auth (admin) | Clerk | Frontend uses Clerk's hosted sign-in; backend verifies the Clerk session JWT on every request — see ADR-007. No passwords touch our code. |
| Auth (device) | Static per-device API key, hashed at rest | Unaffected by Clerk — devices aren't Clerk users, this stays as originally spec'd |
| Rotating codes | TOTP (RFC 6238) via `pyotp` | See ADR-001 |
| Task runner | Uvicorn (dev), Gunicorn+Uvicorn workers (prod) | |
| Local dev | Docker Compose (`db`, `backend`) | |
| Firmware | C/C++, ESP-IDF | See ADR-002 |

## Quickstart (backend)

The database is a Supabase project, not a local container — create one at supabase.com
(free tier is enough for this project's scale) and copy its connection string. Use a
**separate Supabase project for dev and prod**, not the same one — the free tier allows
multiple projects, and sharing one instance between a developer running migrations locally
and a live deployment is how you get a corrupted production database.

```bash
cp .env.example .env        # fill in secrets — see table below, including Supabase and Clerk keys
cd backend
pip install -r requirements.txt
alembic upgrade head        # runs against the Supabase DATABASE_URL in .env
uvicorn app.main:app --reload
```

No `docker compose up -d db` step — there's no local database container. If you'd rather
develop fully offline, the Supabase CLI (`supabase start`) spins up a local Postgres plus
the rest of the Supabase stack in Docker; not required for this project but an option if
connectivity to the hosted project becomes a problem during development.

API docs (auto-generated by FastAPI) will be at `http://localhost:8000/docs`. Treat
[`docs/API_SPEC.md`](docs/API_SPEC.md) as the source of truth for *intended* behavior —
the auto-generated docs reflect whatever is actually implemented, which may lag behind.

## Environment variables

| Variable | Purpose | Example |
|---|---|---|
| `DATABASE_URL` | Supabase Postgres connection string | `postgresql+asyncpg://postgres:pass@db.xxxxx.supabase.co:5432/postgres` — use the pooler connection string (port 6543) if deploying somewhere with many short-lived connections |
| `CLERK_SECRET_KEY` | Backend-side key for verifying Clerk sessions | from the Clerk dashboard, backend only, never shipped to the frontend |
| `CLERK_PUBLISHABLE_KEY` | Frontend-side key for Clerk's hosted sign-in components | from the Clerk dashboard, safe to expose client-side |
| `TOTP_ENCRYPTION_KEY` | Encrypts TOTP secrets at rest (Fernet key) | generate with `Fernet.generate_key()` |
| `RANGE_WEBHOOK_SECRET` | HMAC secret shared with the CTF range for webhook verification | ask whoever runs the range |
| `RATE_LIMIT_PER_MINUTE` | Max code-validation attempts per device per minute | `5` |
| `CORS_ORIGINS` | Allowed frontend origins | `http://localhost:5173` |

Never commit a real `.env`. `TOTP_ENCRYPTION_KEY` and `RANGE_WEBHOOK_SECRET` are the two
secrets that matter most here — if either leaks, the lock's core security property is gone.

## Notes for coding agents

- `docs/DECISIONS.md` is authoritative for anything architectural. If a request conflicts
  with a recorded decision, implement the decision and say so, rather than silently picking
  a different approach.
- `docs/API_SPEC.md` is the contract. Implement exactly what it specifies, including the
  status codes and error shapes — a "business decline" (invalid code) and a "client error"
  (malformed request) are deliberately not the same HTTP status in this spec; don't collapse
  that distinction for convenience.
- The code-validation path (`POST /devices/{device_id}/validate-code`) is the security-critical
  endpoint in this system. Rate limiting and constant-time comparison for the TOTP check are
  not optional nice-to-haves — implement them from the first version, not as a later pass.
